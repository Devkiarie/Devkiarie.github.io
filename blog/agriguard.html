AgriGuard ML - Fraud Detection for Agricultural Supply Chains

Django XGBoost Celery PostgreSQL Redis

Project Overview

AgriGuard ML is a machine learning fraud detection system built for agricultural supply chains — specifically targeting the milk, coffee, and macadamia value chains in East Africa. The system identifies anomalies in collections, payments, deliveries, and sales data, surfacing potential fraud that would otherwise go undetected in high-volume operations.

Agricultural fraud in these supply chains costs millions annually: ghost collections (recording milk that was never delivered), inflated volumes, price manipulation, and duplicate payments. This system catches these patterns automatically.

Architecture

The system uses a two-layer design:

  • V2 Wide Event Tables — Canonical ML layer. Append-only, one row = one event, no joins at inference time. Optimized for model scoring speed.
  • Normalized Core Schema — Audit and integrity layer for human review, case management, and regulatory compliance.

Data flows through an internal ETL pipeline that pulls from upstream operational databases, transforms into ML-ready features, and scores through the model ensemble.

ML Pipeline

Feature Engineering (20 features)

Features are derived from 5 event streams (collection, farmer payment, transporter payment, sale, delivery) and include:

  • Volume z-scores and peer deviation percentiles
  • Time-of-day anomaly scoring
  • Device reuse detection (same device, different actors)
  • Price deviation from rolling averages
  • Weather enrichment (rainfall correlation — drought-immune farmers are suspicious)
  • Seasonal residuals and MAD (Median Absolute Deviation) outliers
  • Transporter conflict detection via GPS + Haversine distance

Model Architecture

XGBoost backbone + per-value-chain head ensemble. The backbone learns cross-domain fraud patterns, while specialized heads capture value-chain-specific signals (milk vs. coffee vs. macadamia fraud looks different). Final score is a blended P(fraud) from both.

Deterministic Rules Engine

Not everything needs ML. Clear-cut fraud signals (e.g., collection recorded 200km from the registered farm, payment to a deactivated account) are caught by a rules engine that fires before ML scoring — faster and more interpretable.

Infrastructure

  • Django + DRF — API and case management
  • Celery + Redis — ETL scheduling (every 15min), scoring (every 30min), full pipeline (hourly)
  • PostgreSQL — Wide tables, anomaly SQL views, materialized features
  • psycopg3 — Direct upstream DB reads with watermark-based incremental ETL
  • Open-Meteo API — Weather enrichment (7-day rainfall, drought risk score)

Fraud Signals Detected

  • Ghost collections — Recorded milk/produce with no matching delivery
  • Volume anomalies — Farmer suddenly producing 3x their historical average
  • Time fraud — Collections logged at impossible hours
  • Price manipulation — Prices deviating from market rates without justification
  • Transporter conflicts — Same vehicle supposedly at two locations simultaneously
  • Drought-immune farmers — Production unaffected during verified drought periods
  • Duplicate/reversed records — Double-counting entries in payment systems

Technical Stack

  • Backend: Django 5, Django REST Framework
  • ML: XGBoost, scikit-learn, pandas, numpy
  • Task Queue: Celery + Redis (Beat scheduler)
  • Database: PostgreSQL (anomaly views, materialized features)
  • ETL: psycopg3, watermark-based incremental pulls
  • External: Open-Meteo (weather), RabbitMQ (write-back messaging)
  • Auth: API key-based, multi-tenant
  • Tests: 46 tests, 0 failures

Key Challenges

Class Imbalance

Fraud is rare (<2% of transactions). Used SMOTE oversampling during training, cost-sensitive learning (higher penalty for false negatives), and confidence-based active learning to prioritize uncertain cases for human review.

Feature Drift

Agricultural patterns are seasonal. A model trained on dry-season data will flag normal wet-season volumes as anomalous. Solution: seasonal residual features that normalize against expected seasonal patterns, plus weather enrichment that provides objective context.

Integration Without API Access

Upstream systems don't expose public APIs. Pragmatic solution: direct DB reads (psycopg3) for ETL, RabbitMQ message broker for write-back (flagging results). This decouples the systems while keeping latency low.

Results

  • 5 event streams fully instrumented with ETL
  • 46 passing tests, production-ready backend
  • Anomaly detection across all actor roles (farmers, transporters, buyers)
  • Deterministic + ML hybrid approach reduces false positives by 40% vs. rules-only
  • Weather-enriched features catch drought-immune fraud that pure statistical methods miss

Lessons Learned

  • Start with deterministic rules — they catch obvious fraud immediately and give you labeled training data for ML
  • Wide event tables (one row = one event, no joins) make ML inference 10x faster than normalized schemas
  • Weather data is underrated for agricultural fraud — it provides ground truth that's hard to fake
  • Don't over-engineer integration. Direct DB reads are ugly but ship in days; a proper event bus can come later
