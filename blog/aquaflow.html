AquaFlow - Industrial Water Treatment HMI

ESP32 MQTT React Docker Node.js

Project Overview

AquaFlow is a complete industrial water treatment monitoring and control system. It combines custom ESP32 firmware, MQTT telemetry, a Node.js/Fastify backend, and a React-based Human-Machine Interface (HMI) dashboard — all containerized with Docker for deployment flexibility.

The physical system manages 5 tanks in a treatment cascade (T0 through T4), 3 pumps for inter-tank transfer, and multiple sensor types (ultrasonic + resistive water level). The HMI provides real-time visualization, manual pump control, and automated safety interlocks.

System Architecture

The water flows through a closed loop: T0 (source) -> T1/T2 (primary) -> T3 (treatment) -> T4 (output), with a return pump (T4 -> T1) for recirculation.

  • ESP32-S3 DevKitC-1 — Firmware (C/Arduino), sensor reading, pump relay control, MQTT publishing
  • Mosquitto MQTT Broker — Message bus between firmware and server (500ms telemetry interval)
  • Node.js/Fastify Server — MQTT subscriber, WebSocket bridge to HMI, command relay, data logging
  • React HMI Dashboard — Real-time tank levels, pump states, manual controls, alarm history
  • Docker Compose — All services containerized (server :3001, HMI :8080, MQTT :1883)

Firmware Deep Dive

Sensor Strategy

Two sensor types were tested and deployed:

  • Resistive water sensors (T1, T4) — Reliable, cheap, ADC-based. Each unit has different dry/wet baselines requiring individual calibration.
  • HC-SR04 ultrasonic (T2, T3) — Non-contact but unreliable in ESP32 FreeRTOS context. Standard pulseIn() fails because WiFi task preemption misses short echo pulses (~870us for 15cm).

Solution for ultrasonics: ISR-based echo timing with hardware interrupts. The ISR captures the exact microsecond timestamps of rising/falling edges, immune to task scheduling.

Safety Interlocks

Firmware implements hard safety rules that override all commands:

  • Dry-run guard: Pump won't start if source tank < 10% (protects pump from running dry)
  • Overflow guard: Pump stops if destination tank > 90%
  • Relay polarity: Active-HIGH (GPIO HIGH = pump ON). Documented because the relay module datasheet says active-LOW but the actual wiring is inverted.

Power/Ground Architecture

A critical lesson learned: USB power + buck converter 5V simultaneously creates a ground loop that prevents relay GPIOs from driving properly. Solution: USB-only during development, buck converter powers relay/sensor/LCD through a star-point ground. Never connect both to ESP32 simultaneously.

HMI Dashboard

The React dashboard provides:

  • Real-time tank level visualization (animated fill levels)
  • Pump status indicators with manual ON/OFF controls
  • Historical data charts (level trends over time)
  • Alarm panel (overflow warnings, dry-run alerts, sensor failures)
  • System configuration (calibration values, safety thresholds)

Data flows from ESP32 -> MQTT -> Fastify server -> WebSocket -> React at 500ms intervals, providing near-real-time updates.

Technical Stack

  • Firmware: ESP32-S3, Arduino framework, FreeRTOS, ISR-based sensors
  • Communication: MQTT (Mosquitto), WebSocket
  • Backend: Node.js, Fastify
  • Frontend: React, real-time WebSocket updates
  • Infrastructure: Docker Compose (3 containers)
  • OTA Updates: ArduinoOTA (aquaflow.local)
  • Hardware: Resistive water sensors, HC-SR04 ultrasonic, relay modules, I2C LCD (PCF8574)

Key Challenges

FreeRTOS vs. Timing-Critical Sensors

The biggest firmware challenge. ESP32 runs WiFi, MQTT, and sensor tasks concurrently via FreeRTOS. Ultrasonic sensors need microsecond-precise timing for echo pulses. Task preemption during pulseIn() causes missed readings. ISR-based approach solved this completely.

Ground Loops in Mixed-Power Systems

When USB (for programming) and buck converter (for relays/sensors) both power the ESP32, the different ground potentials create noise that makes GPIO outputs unreliable for relay driving. Star-point grounding and never connecting both power sources simultaneously was the fix.

Sensor Calibration Variance

Every resistive water sensor has a different baseline. One reads 373 dry / 1685 wet, another reads 500 dry / 988 wet. Each requires individual calibration — there's no universal threshold.

Results

  • 5-tank water treatment system fully automated
  • 500ms telemetry providing near-real-time monitoring
  • Safety interlocks preventing dry-run and overflow conditions
  • Docker deployment — spin up the entire server stack with one command
  • OTA firmware updates — no physical access needed for firmware changes

Lessons Learned

  • pulseIn() is fundamentally broken in FreeRTOS with WiFi — always use ISR for timing-critical operations
  • Never trust relay module datasheets at face value — test actual polarity with a multimeter
  • Star-point grounding is non-negotiable when mixing logic and power circuits
  • Calibrate each sensor individually — "typical" values from datasheets are meaningless for precision work
  • MQTT at 500ms is the sweet spot for industrial HMI — fast enough for human reaction, not so fast it floods the network
